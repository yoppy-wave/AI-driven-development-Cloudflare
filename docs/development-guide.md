# 開発ガイド

この文書は、開発者とレビュー担当者が日々の作業を進めるための手順です。端末準備は[開発者セットアップ](developer-setup.md)、GitHub・AWSの初期設定は[GitHubリポジトリの初回設定](github-repository-setup.md)を参照してください。

AIツールは調査・計画・実装・検証を支援しますが、要求の優先順位、設計上のトレードオフ、認証・権限・AWS操作、レビューとマージの判断は人間が担います。

## 共通の開発フロー

1. **Issue・要求を確認する**: 目的、受け入れ条件、影響範囲、制約を確認します。不明点や優先順位は担当者へ確認します。
2. **作業ブランチを作成する**: 採用しているブランチ運用に従います。
3. **既存コードを調査し、計画を作る**: AIを使う場合も、関連実装、テスト、設定、既存の設計資料を調べます。変更対象、テスト方針、リスクを整理します。
4. **人間が必要な判断を行う**: 要求の解釈、外部仕様、データ移行、セキュリティ、費用、AWS操作、破壊的変更は、必要な責任者の判断・承認を得ます。
5. **実装する**: 開発者またはAIが、既存の設計・命名・ルールに従って実装します。AIが作成した変更も作成者が内容を確認します。
6. **テスト・静的検査を行う**: 変更に対応した単体テストを追加し、関連する回帰テスト、型チェック、ビルド・synthを実行します。
7. **コミット・push・PRを作成する**: 変更の意図と検証結果が分かる単位でコミットし、PRに目的、主な変更、テスト結果、確認が必要な点を記載します。
8. **レビューとCIを確認する**: レビュー指摘、必須チェック、CI結果を確認し、必要に応じて修正します。
9. **マージして完了する**: 必要な承認とCI成功を確認してからマージします。Issue、リリースノート、運用手順の更新が必要なら完了前に反映します。

Pythonの単一実装・設定ファイルを主に検証するテストは、実装ファイルと同じディレクトリに`<実装ファイル名>_test.py`として配置します。複数ファイルやworkflow全体を横断するテストは`tests/`に置きます。

## ブランチ運用

### 個人開発（main中心）

現在の初期状態では`main`を中心に運用できます。小さく自己完結した変更は、必要に応じて`main`上または短命な作業ブランチで進めます。将来の共同作業、レビュー、リリースを見据える場合は、早い段階からPRを使い、変更を小さく保ちます。

`main`へのpushはApplication CI/CDのdevelopmentデプロイ入口ですが、現在は`.github/cicd/application.json`でCDK・デプロイが無効です。AWS有効化前後を問わず、明示承認なしにローカルからAWS認証、`cdk deploy`、`cdk destroy`、`cdk bootstrap`を実行しません。

### チーム開発（feature/fix → stg → prod）

GitHub Rulesetを有効化したチーム開発では、次の流れを使います。

```text
stg を最新化
  → stg から feature/<内容> または fix/<内容> を作成
  → 実装・検証・commit・push
  → feature/* または fix/* から stg へのPR
  → レビュー・CI成功後に stg へマージ
  → 統合・検証
  → stg から prod へのPR
  → PO承認・CI成功後、リリース責任者が prod へマージ
```

`stg`と`prod`へのマージはGitHub上のPRを通じて行います。RulesetとPRポリシーは、直接pushや許可されないPR元をサーバー側で拒否する設定です。詳細な有効化要件は[GitHubリポジトリの初回設定](github-repository-setup.md#2-ブランチとpr保護)を参照してください。

## ローカル検証

Dev Container内で、変更内容に応じて少なくとも関連する検証を実行します。現時点の共通コマンドは次のとおりです。

```bash
npm run typecheck
npm test
python -m pytest
npm run synth
```

初回または依存関係を更新した場合は、先に次を実行します。

```bash
npm ci
python -m pip install -r requirements-dev.lock
```

CIは全ブランチへのpushとPRでTest・Lint・Dependency・Securityを並列実行します。Testでは検出したPython・Node.jsプロジェクトのテスト、型チェック、build、synthを実行し、Lintは独立したゲートで検証します。全ゲート成功後だけ後続処理へ進みます。`stg`または`prod`宛てPRのPRポリシーも維持します。ランタイムの3日ルール、固定依存、Securityの検出範囲、ローカル実行方法は[CI品質ゲート](ci-quality-gates.md)を参照してください。テストが期待する振る舞いを十分に表しているかは、CI成功だけでなくレビューでも確認します。

## IssueからAIを利用する

AI Issueワークフローは、プロジェクト管理者が必要なラベルとSecretsを設定している場合だけ利用できます。設定方法は[GitHubリポジトリの初回設定](github-repository-setup.md#3-github-actionsai-issueワークフローsecrets)を参照してください。

### Issueの質問にAIで回答する

1. Issueに質問、前提、期待する回答を記載します。
2. Issue全体への質問は`ai-question`ラベルを付けます。既に付いているIssueで再実行する場合は、一度外してから付け直します。
3. 会話の続きとして質問する場合は、OWNER、MEMBER、COLLABORATORが`@cline 質問内容`とコメントします。各コメントは個別にキューへ入り、そのコメントまでのIssue本文・会話履歴を踏まえて1回ずつ回答します。Cline自身のコメントでは再実行しません。
4. workflowは既定ブランチを調査し、回答を同じIssueへコメントします。読み取り以外のツール操作と、作業ツリーを変更した場合の投稿は停止する構成です。
5. 現在のようにアプリケーションコードがない場合、回答はその事実を前提にします。Cline CLIの処理に失敗した場合、回答コメントは投稿されません。

### IssueからAIに実装を依頼する

1. Issueに目的、受け入れ条件、制約、必要なら対象範囲を記載します。
2. `ai-coding`ラベルを付けます。
3. workflowは既定ブランチの既存コードとテストを確認し、計画、実装、関連チェックを行います。
4. 変更があれば`ai-coding/issue-<番号>`ブランチのドラフトPRを作成または更新し、IssueをPR本文から参照します。既定ブランチへ直接反映しません。変更がなければ、報告をIssueへコメントします。
5. 作成されたPRは人間が必ずレビューし、通常のCI・承認手順を満たしてからマージします。

この自動実装は`.github/`配下の変更をPR化せず停止します。workflowやAI向け指示ファイルの変更は、別途人間がレビューして行ってください。AI実装workflowはコマンドを実行できるため、APIキーの利用上限を設定し、信頼できる担当者だけがラベルを付けるようにします。

## PR作成前・マージ前の確認

### 作成前

- [ ] 要求・受け入れ条件・影響範囲を確認した
- [ ] 既存実装と関連テストを調査し、必要な人間の判断・承認を得た
- [ ] 変更に対応するテストを追加または更新した
- [ ] 関連する単体テスト、回帰テスト、型チェック、ビルド・synthを実行した
- [ ] 秘密情報、生成物、不要な変更を含めていない

### マージ前

- [ ] PR本文に目的、主な変更、検証結果、残る確認事項を記載した
- [ ] CIが成功し、レビュー指摘と会話を解決した
- [ ] チーム開発ではRulesetに必要な承認を得た
- [ ] AWSや本番相当の変更では、対象・影響・復旧方法について必要な承認を得た
- [ ] マージ後に必要なIssue更新、リリース作業、運用連絡を確認した
